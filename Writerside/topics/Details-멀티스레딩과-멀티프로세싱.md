# Details: 멀티스레딩과 멀티프로세싱

여러 작업을 동시에 실행하는 방법은 크게 두 가지입니다. 한 프로세스 안에서 스레드를 여러 개 돌리는 멀티스레딩, 그리고 프로세스 자체를 여러 개 돌리는 멀티프로세싱입니다. 둘의 차이는 결국 "메모리를 같이 쓰느냐, 따로 쓰느냐"에서 나옵니다.

## 프로세스와 스레드 {#process-and-thread}

프로세스는 실행 중인 프로그램 하나입니다. 운영체제는 프로세스마다 독립된 메모리 공간(주소 공간)을 주고, 열린 파일 같은 자원도 프로세스 단위로 관리합니다. 한 프로세스는 다른 프로세스의 메모리를 직접 읽거나 쓸 수 없습니다.

스레드는 프로세스 안에서 코드를 실행하는 흐름입니다. 프로세스 하나에 스레드가 여러 개 있을 수 있고, 같은 프로세스의 스레드들은 힙 메모리와 자원을 함께 씁니다. 스레드마다 따로 갖는 것은 자기 호출 스택과 CPU 레지스터 상태 정도입니다.

## 메모리 공유와 통신 {#memory}

**멀티스레딩**에서는 스레드들이 같은 메모리를 보므로, 한 스레드가 만든 객체를 다른 스레드가 그대로 쓸 수 있습니다. 데이터를 주고받기가 빠르고 쉽습니다. 대신 여러 스레드가 같은 데이터를 동시에 고치면 결과가 실행 순서에 따라 달라지는 레이스 컨디션(race condition)이 생길 수 있고, 이를 막으려고 락을 쓰다 보면 서로가 가진 락을 기다리며 영원히 멈추는 데드락(deadlock)이 생길 수 있습니다. 공유 데이터를 다루는 방법은 [코루틴과 가변 상태](Details-코루틴과-가변-상태.md)에서 이어집니다.

**멀티프로세싱**에서는 프로세스마다 메모리가 따로라서 이런 충돌이 원천적으로 없습니다. 대신 데이터를 주고받으려면 운영체제가 제공하는 프로세스 간 통신(<tooltip term="IPC">IPC</tooltip>)을 거쳐야 합니다. 데이터를 바이트로 바꿔 보내고 받는 쪽에서 다시 객체로 만들어야 하므로 느리고 코드도 복잡해집니다.

안드로이드가 좋은 예입니다. 앱은 기본적으로 자기 프로세스 하나에서 돌지만, `AndroidManifest.xml`에서 컴포넌트에 `android:process` 속성을 주면 별도 프로세스에서 실행할 수 있습니다([Q32) Android의 프로세스](Q32-Android의-프로세스.md)). 이렇게 나누면 메모리가 분리되므로, 한쪽 프로세스에서 만든 싱글톤 객체나 전역 변수 값이 다른 프로세스에서는 보이지 않습니다. 두 프로세스가 데이터를 주고받으려면 바인더(Binder) 기반의 AIDL, `Messenger`, `ContentProvider` 같은 IPC 수단을 써야 하고, 넘기는 객체는 `Parcelable`로 바이트 형태로 바꿔야 합니다.

## 실행과 전환 비용 {#execution}

스레드와 프로세스 모두 운영체제가 선점형으로 스케줄링합니다. 차이는 전환 비용입니다. 같은 프로세스의 스레드끼리 바꿀 때는 메모리 공간이 그대로라 레지스터와 스택 위치만 바꾸면 됩니다. 다른 프로세스로 바꿀 때는 메모리 공간 자체를 바꿔야 해서, 주소 변환 정보를 다시 불러오는 등 할 일이 더 많습니다.

만드는 비용도 프로세스가 큽니다. 새 프로세스는 메모리 공간과 자원 목록을 통째로 새로 갖춰야 합니다. 안드로이드는 이 비용을 줄이려고 미리 런타임과 공통 클래스를 올려 둔 자이고트(Zygote) 프로세스를 복제(fork)해서 앱 프로세스를 만듭니다.

## CPU 작업과 I/O 작업 {#cpu-vs-io}

책은 멀티스레딩이 I/O 작업에, 멀티프로세싱이 여러 코어를 쓰는 CPU 작업에 맞는다고 정리합니다. 이 구분은 파이썬처럼 한 프로세스 안에서 한 번에 한 스레드만 코드를 실행할 수 있게 막는 언어에서 나온 것입니다(파이썬의 GIL). 그런 언어에서는 스레드를 늘려도 계산이 빨라지지 않으니 프로세스를 늘려야 합니다.

JVM과 안드로이드 런타임에는 그런 제약이 없어서, 한 프로세스의 여러 스레드가 여러 코어에서 동시에 계산합니다. 소수 개수를 세는 계산을 스레드 하나로 할 때와, 여덟 구간으로 나눠 `Dispatchers.Default`(코어 수만큼의 스레드)에서 동시에 할 때를 비교했습니다.

```kotlin
// CpuBound.kt
import kotlinx.coroutines.*
import kotlin.system.measureTimeMillis

fun countPrimes(from: Int, to: Int): Int {
    var count = 0
    for (n in from until to) {
        if (n < 2) continue
        var prime = true
        var d = 2
        while (d * d <= n) { if (n % d == 0) { prime = false; break }; d++ }
        if (prime) count++
    }
    return count
}

suspend fun parallel(n: Int, chunks: Int) = coroutineScope {
    (0 until chunks).map { i ->
        async(Dispatchers.Default) { countPrimes(i * n / chunks, (i + 1) * n / chunks) }
    }.awaitAll().sum()
}

fun main() = runBlocking {
    val n = 5_000_000
    repeat(3) { countPrimes(0, n); parallel(n, 8) }   // JIT 워밍업

    val one = measureTimeMillis { countPrimes(0, n) }
    val many = measureTimeMillis { parallel(n, 8) }
    println("스레드 1개: ${one}ms")
    println("8등분해 Dispatchers.Default 에서: ${many}ms")
}
```

```text
스레드 1개: 441ms
8등분해 Dispatchers.Default 에서: 91ms
```

12코어 맥에서 약 4.8배 빨라졌습니다. 뒤 구간일수록 숫자가 커서 계산이 많으므로 8배까지는 나오지 않았지만, 한 프로세스 안의 스레드만으로 여러 코어를 쓴 것은 분명합니다. JVM에서 멀티프로세싱을 고르는 이유는 계산 속도보다는 아래의 장애 격리나 메모리 분리 쪽입니다.

## 장애 격리와 확장 {#isolation}

멀티스레딩에서는 한 스레드의 문제가 프로세스 전체로 번지기 쉽습니다. 메모리를 같이 쓰므로 한 스레드가 데이터를 망가뜨리면 다른 스레드도 영향을 받습니다. 안드로이드는 여기서 더 나아가, 어느 스레드에서든 잡히지 않은 예외가 나면 기본 예외 처리기가 앱 프로세스 전체를 종료시킵니다. 백그라운드 스레드의 예외 하나로 앱이 꺼지는 것이 이 때문입니다. 일반 JVM에서는 기본적으로 예외가 난 스레드만 끝나고 프로세스는 계속 돕니다.

멀티프로세싱에서는 한 프로세스가 죽어도 다른 프로세스는 계속 돕니다. 크롬 브라우저가 탭마다 프로세스를 나누는 것도, 안드로이드 앱이 불안정한 외부 라이브러리나 무거운 작업을 별도 프로세스로 떼어 내는 것도 이런 격리를 얻기 위해서입니다.

확장 면에서도 차이가 있습니다. 스레드는 한 프로세스, 한 기기 안에서만 늘릴 수 있습니다. 프로세스는 처음부터 메모리를 나눠 쓰고 메시지로 통신하는 구조라 여러 기기로 나눠 돌리기도 쉽습니다.

## 요약 {#summary}

| 관점 | 멀티스레딩 | 멀티프로세싱 |
|---|---|---|
| 메모리 | 같은 프로세스의 힙을 함께 씁니다 | 프로세스마다 따로입니다 |
| 데이터 주고받기 | 객체를 그대로 공유해 빠르지만 레이스 컨디션·데드락을 조심해야 합니다 | IPC를 거쳐야 해서 느리고 복잡하지만 충돌이 없습니다 |
| 만들기·전환 비용 | 작습니다 | 큽니다 |
| 장애 | 한 스레드의 문제가 프로세스 전체로 번질 수 있습니다 | 한 프로세스가 죽어도 다른 프로세스는 계속 돕니다 |
| 여러 코어 활용 | JVM·안드로이드에서는 스레드만으로 가능합니다 | 가능하며, 여러 기기로 나누기도 쉽습니다 |

안드로이드 앱 개발에서 기본은 한 프로세스 안의 멀티스레딩(그리고 그 위의 코루틴)이고, 멀티프로세싱은 장애 격리나 메모리 분리가 필요할 때 `android:process`로 선택하는 수단입니다.
