# Q33) 코루틴과 스레드의 차이

Q31에서 코루틴이 스레드보다 가볍고, 정해진 지점에서 스스로 실행을 넘긴다는 것을 짧게 봤습니다. 이 토픽에서는 그 차이를 세 가지 관점으로 나눠 자세히 봅니다. 누가 만들고 관리하는지, 누가 언제 실행을 바꾸는지, 기다리는 동안 무엇이 메모리를 차지하는지입니다. 마지막으로 두 개념이 경쟁 관계가 아니라 위아래로 쌓인 관계라는 점을 정리합니다.

예제는 Kotlin 2.4.21, kotlinx-coroutines 1.11.0, JDK 25, macOS(Apple Silicon, 12코어)에서 실행했습니다. 스레드 개수 한도나 스택 크기처럼 운영체제와 JVM 설정에 따라 달라지는 숫자는 그렇다고 표시했습니다.

## 생성과 관리 {#creation}

**스레드는 운영체제가 만들고 관리합니다.** 자바나 코틀린에서 `Thread`를 시작하면 JVM이 운영체제에 스레드를 만들어 달라고 요청합니다(시스템 콜). 운영체제는 스레드를 관리할 자료 구조를 만들고, 그 스레드 전용 스택 메모리를 잡고, 스케줄러에 등록합니다. 스택 크기는 JVM 설정으로 정해지며, 이 환경(JDK 25, macOS)의 기본값은 2MB입니다(`ThreadStackSize = 2048`KB). 리눅스 64비트 JVM의 기본값은 1MB입니다.

**코루틴은 라이브러리가 만드는 평범한 객체입니다.** `launch`로 코루틴을 시작해도 시스템 콜은 일어나지 않습니다. 코루틴 하나를 나타내는 객체와, Q32에서 본 상태 객체(`Continuation`)가 힙에 생길 뿐입니다. 상태 객체에는 다음에 이어 갈 위치(`label`)와 일시 중단 지점을 넘어 쓰이는 지역 변수만 들어 있습니다.

차이는 개수를 늘려 보면 드러납니다. 책의 예제처럼 각자 1초씩 기다리는 스레드를 10만 개 만들어 봤습니다.

```kotlin
// Threads.kt
import java.util.concurrent.atomic.AtomicInteger

fun main() {
    val started = AtomicInteger()
    try {
        repeat(100_000) {
            Thread {
                started.incrementAndGet()
                Thread.sleep(1000L)
            }.start()
        }
        println("10만 개 모두 시작")
    } catch (e: Throwable) {
        println("${started.get()}개 시작 후 실패: $e")
        System.exit(1)
    }
}
```

```text
4066개 시작 후 실패: java.lang.OutOfMemoryError: unable to create native thread: possibly out of memory or process/resource limits reached
```

4천 개 남짓에서 더 이상 스레드를 만들지 못했습니다. 이 맥은 프로세스 하나가 가질 수 있는 스레드 수를 4096개로 제한하고 있어서(`sysctl kern.num_taskthreads`), 메모리보다 이 한도에 먼저 걸렸습니다. 오류 이름은 `OutOfMemoryError`지만 메시지에 적힌 대로 메모리 부족이나 프로세스 자원 한도 중 하나에 걸렸다는 뜻입니다. 한도는 운영체제마다 다르고, 한도가 넉넉한 환경이라면 스택 메모리가 먼저 문제가 됩니다.

같은 일을 코루틴으로 하면 이렇습니다.

```kotlin
// Coroutines.kt
import kotlinx.coroutines.*

// 지금 쓰고 있는 힙 크기(MB). 정확히 재려고 GC를 몇 번 돌린 뒤 잽니다
fun usedHeapMb(): Long {
    repeat(3) {
        System.gc()
        Thread.sleep(50)
    }
    val runtime = Runtime.getRuntime()
    return (runtime.totalMemory() - runtime.freeMemory()) / 1_000_000
}

fun main() = runBlocking {
    val before = usedHeapMb()
    val jobs = List(100_000) {
        launch { delay(1000L) }
    }
    delay(500)   // 10만 개가 모두 delay 에서 일시 중단된 상태
    val during = usedHeapMb()
    println("코루틴 10만 개 일시 중단 중: 힙 ${during - before}MB 증가, 스레드 ${Thread.activeCount()}개")
    jobs.joinAll()
    println("모두 완료")
}
```

```text
코루틴 10만 개 일시 중단 중: 힙 32MB 증가, 스레드 1개
모두 완료
```

10만 개가 동시에 기다리는 동안 힙은 약 32MB 늘었습니다. 코루틴 하나에 300바이트 남짓입니다. 스레드는 `main` 하나로 충분했습니다. 스레드 하나의 스택으로 잡는 2MB에 비하면 몇천 분의 일 수준입니다.

스택 크기 2MB는 스레드마다 미리 잡아 두는(예약하는) 주소 공간의 크기이고, 실제 물리 메모리는 스택을 깊게 쓸수록 조금씩 채워집니다. 그래서 "스레드 하나가 항상 2MB를 차지한다"는 말은 과장입니다. 그래도 스레드마다 커널 자료 구조와 스택이 따로 필요하고 개수 한도가 있다는 점은 그대로입니다.

## 스케줄링과 전환 {#scheduling}

**스레드는 선점형으로 스케줄링됩니다.** 운영체제 스케줄러는 실행 중인 스레드를 거의 아무 지점에서나 멈추고 다른 스레드로 바꿀 수 있습니다. 이를 선점(preemption)이라고 합니다. 바꿀 때는 지금 스레드의 CPU 레지스터, 다음에 실행할 명령 위치, 스택 위치를 저장하고 다음 스레드의 것을 불러옵니다. 이 과정을 컨텍스트 스위치(context switch)라고 부릅니다. 커널로 들어갔다 나와야 하고, 다른 스레드가 쓰던 데이터로 CPU 캐시가 채워지면서 느려지는 비용도 생깁니다.

**코루틴은 협력형으로 스케줄링됩니다.** 코루틴은 일시 중단 지점에 닿을 때까지 지금 스레드에서 계속 실행됩니다. 일시 중단 지점에서 Q32의 상태 머신이 상태를 저장하고 `COROUTINE_SUSPENDED`를 반환하면, 스레드는 디스패처에게 돌아가 다음 코루틴을 실행합니다. 커널이 끼어들지 않는 같은 프로세스 안의 메서드 반환과 호출이라 비용이 작습니다.

협력형이라는 말은 코루틴이 실행을 넘겨 주지 않으면 아무도 빼앗지 않는다는 뜻이기도 합니다. 일시 중단 지점이 없는 긴 계산은 그동안 스레드를 내주지 않습니다.

```kotlin
// Busy.kt
import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
    launch {
        repeat(3) { i ->
            var x = 0L
            repeat(300_000_000) { x += it }   // 일시 중단 지점이 없는 계산
            println("계산 $i 끝")
        }
    }
    launch { println("다른 코루틴") }
}
```

```text
계산 0 끝
계산 1 끝
계산 2 끝
다른 코루틴
```

두 코루틴이 `main` 스레드 하나를 나눠 쓰는데, 첫 번째 코루틴이 계산을 다 끝낼 때까지 두 번째는 시작도 못 했습니다. 스레드였다면 운영체제가 중간중간 바꿔 줬을 것입니다. 코루틴에서는 반복마다 `yield()`처럼 일시 중단 지점을 넣어 직접 실행을 넘기거나, 계산을 여러 스레드를 가진 디스패처로 보내야 합니다.

## 기다리는 동안의 상태와 메모리 {#waiting}

**스레드는 기다리는 동안 블로킹됩니다.** 스레드가 네트워크 응답이나 락을 기다리면 운영체제는 그 스레드를 대기 상태로 둡니다. 대기 중인 스레드는 다른 일을 할 수 없지만 스택과 커널 자원은 그대로 붙잡고 있습니다. 응답을 기다리는 요청이 100개면, 요청마다 스레드를 쓰는 방식에서는 대기 중인 스레드도 100개입니다.

**코루틴은 기다리는 동안 일시 중단됩니다.** 코루틴은 실행 중일 때만 스레드를 쓰고, 일시 중단되면 상태를 힙의 상태 객체에 남기고 스레드를 놓아줍니다. 이 점에서 코틀린 코루틴을 스택리스(stackless) 코루틴이라고 부릅니다. 코루틴마다 전용 호출 스택을 두지 않고, Q32에서 본 `Continuation` 사슬이 "끝나면 어디로 돌아갈지"를 대신 기억하기 때문입니다. 반대로 고(Go) 언어의 고루틴처럼 코루틴마다 작은 전용 스택을 두고 필요하면 늘리는 방식을 스택풀(stackful)이라고 합니다.

그렇다고 코루틴 안이면 무엇이든 스레드를 놓아주는 것은 아닙니다. 스레드를 놓아주는 것은 `delay`, `await`처럼 일시 중단하는 함수뿐이고, `Thread.sleep`이나 블로킹 I/O 함수는 코루틴 안에서도 스레드를 붙잡습니다.

```kotlin
// Blocking.kt
import kotlinx.coroutines.*

fun threadName() = Thread.currentThread().name

fun main() = runBlocking<Unit> {
    val start = System.currentTimeMillis()
    fun elapsed() = System.currentTimeMillis() - start   // 시작부터 지난 시간(ms)

    launch {
        Thread.sleep(500)   // 코루틴이 아니라 main 스레드 자체를 멈춥니다
        println("A 끝 ${elapsed()}ms [${threadName()}]")
    }
    launch {
        Thread.sleep(500)
        println("B 끝 ${elapsed()}ms [${threadName()}]")
    }
}
```

```text
A 끝 512ms [main]
B 끝 1023ms [main]
```

`delay(500)`였다면 둘 다 약 500ms에 끝났을 것입니다. `Thread.sleep`은 `main` 스레드 자체를 멈추므로 B는 A가 끝날 때까지 시작하지 못해 약 1초에 끝났습니다. 블로킹 함수를 써야 한다면 `Dispatchers.IO`처럼 블로킹을 감안해 스레드를 넉넉히 둔 디스패처로 보내야 합니다.

세 관점을 표로 정리하면 다음과 같습니다.

| 관점 | 스레드 | 코루틴 |
|---|---|---|
| 생성과 관리 | 운영체제가 만들고 관리합니다. 시스템 콜과 전용 스택이 필요하고 개수 한도가 있습니다 | 라이브러리가 힙에 객체로 만듭니다. 10만 개에 약 32MB였습니다 |
| 전환 | 선점형. 운영체제가 아무 때나 바꾸며 컨텍스트 스위치 비용이 있습니다 | 협력형. 일시 중단 지점에서만 바뀌며 메서드 반환과 호출로 이루어집니다 |
| 기다리는 동안 | 블로킹되어 스레드와 스택을 붙잡고 있습니다 | 일시 중단되어 상태만 힙에 남기고 스레드를 놓아줍니다 |

## JVM의 가상 스레드 {#virtual-threads}

"스레드는 무겁다"는 말은 운영체제 스레드에 해당합니다. JDK 21부터는 JVM이 직접 관리하는 가상 스레드(virtual thread)가 정식 기능이 되었습니다. 가상 스레드는 적은 수의 운영체제 스레드 위에서 돌고, 블로킹 호출을 만나면 JVM이 그 가상 스레드의 스택을 힙에 옮겨 두고 운영체제 스레드를 놓아줍니다. 스택을 통째로 저장한다는 점에서 스택풀 방식입니다.

```kotlin
// Virtual.kt (JDK 21 이상)
fun main() {
    val start = System.currentTimeMillis()
    val threads = List(100_000) {
        Thread.ofVirtual().start { Thread.sleep(1000L) }
    }
    threads.forEach { it.join() }
    println("가상 스레드 10만 개: ${System.currentTimeMillis() - start}ms")
}
```

```text
가상 스레드 10만 개: 1488ms
```

같은 10만 개인데 운영체제 스레드와 달리 문제없이 끝났습니다. 즉 "가볍다"는 성질은 코루틴만의 것이 아니라 "운영체제가 아닌 런타임이 관리하고, 기다리는 동안 운영체제 스레드를 놓아준다"는 구조에서 나옵니다. 코틀린 코루틴은 여기에 더해 구조화된 동시성, 취소, 디스패처 전환 같은 도구를 라이브러리로 제공하고, JVM 외의 플랫폼에서도 같은 코드로 동작합니다.

## 코루틴과 스레드의 관계 {#relationship}

코루틴과 스레드는 둘 중 하나를 고르는 관계가 아닙니다. CPU에서 실행되는 코드는 언제나 어떤 스레드 위에서 실행되고, 코루틴도 마찬가지입니다. 코루틴은 "할 일과 그 진행 상태"를 담은 객체이고, 스레드는 그 일을 실제로 실행하는 일꾼입니다.

어느 일꾼에게 맡길지는 디스패처가 정합니다.

- `Dispatchers.Default`: CPU 코어 수만큼의 스레드로 계산 작업을 돌립니다.
- `Dispatchers.IO`: 블로킹 I/O를 감안해 스레드를 더 많이 쓸 수 있는 풀입니다.
- `Dispatchers.Main`: 안드로이드의 메인(UI) 스레드에서 실행합니다.

코루틴이 일시 중단되면 그 스레드는 다른 코루틴을 실행하고, 재개될 때는 디스패처가 고른 스레드에서 이어 갑니다. 같은 스레드일 수도 있고 다른 스레드일 수도 있습니다. Q32에서 본 것처럼 재개 요청은 디스패처를 거쳐 정해진 스레드로 전달됩니다.

식당에 비유하면 이렇습니다. 테이블마다 종업원을 한 명씩 붙이면, 주방에서 음식이 나오길 기다리는 동안 종업원은 테이블 옆에 서 있기만 합니다. 테이블 10개에 종업원 10명이 필요합니다. 이것이 요청마다 스레드를 쓰는 방식입니다. 종업원 한 명이 1번 테이블 주문을 주방에 넣고 기다리지 않고 2번, 3번 테이블 주문을 받다가, 1번 음식이 나왔다는 알림을 받으면 그때 1번으로 가서 서빙하는 것이 코루틴 방식입니다. 종업원이 스레드, 각 테이블의 주문 처리 과정이 코루틴입니다. 다만 한 테이블에서 아주 오래 붙잡혀 있으면(일시 중단 없는 긴 계산이나 블로킹 호출) 다른 테이블은 그동안 기다려야 합니다.

## 요약 {#summary}

스레드는 운영체제가 관리하는 실행 단위로, 만들 때 시스템 콜과 전용 스택이 필요하고 개수 한도가 있습니다. 운영체제가 아무 때나 실행을 바꾸는 선점형이며, 기다리는 동안 블로킹되어 자원을 붙잡고 있습니다. 이 맥에서는 운영체제 스레드 10만 개를 만들려다 4천여 개에서 실패했습니다.

코루틴은 라이브러리가 힙에 만드는 객체로, 10만 개가 동시에 기다려도 힙 약 32MB와 스레드 하나로 충분했습니다. 일시 중단 지점에서만 실행을 넘기는 협력형이라 전환 비용이 작지만, 일시 중단 지점이 없는 긴 계산이나 `Thread.sleep` 같은 블로킹 호출은 스레드를 붙잡습니다. 코틀린 코루틴은 전용 스택 없이 `Continuation` 사슬로 상태를 남기는 스택리스 방식입니다.

코루틴은 스레드를 대신하는 것이 아니라 스레드 위에서 실행되며, 어느 스레드에서 실행하고 재개할지는 디스패처가 정합니다.

<def title="Q) 코루틴이 스레드보다 가볍다고 하는 이유는 무엇인가요?">

스레드는 운영체제가 만들기 때문에 시스템 콜이 필요하고, 스레드마다 전용 스택(이 환경의 JVM 기본값 2MB)과 커널 자료 구조가 따로 잡히며, 프로세스당 개수 한도도 있습니다. 실제로 이 맥에서는 스레드 10만 개를 만들려다 4천여 개에서 실패했습니다.

코루틴은 라이브러리가 힙에 만드는 객체이고, 일시 중단될 때 다음 위치와 필요한 지역 변수만 상태 객체에 남깁니다. 코루틴 10만 개가 동시에 기다려도 힙은 약 32MB 늘었고 스레드는 하나로 충분했습니다.

</def>
<def title="Q) 선점형 스케줄링과 협력형 스케줄링은 어떻게 다른가요?">

선점형에서는 운영체제 스케줄러가 실행 중인 스레드를 거의 아무 지점에서나 멈추고 다른 스레드로 바꿉니다. 바꿀 때 레지스터와 실행 위치를 저장하고 복원하는 컨텍스트 스위치가 일어나며, 커널을 거쳐야 해서 비용이 큽니다.

협력형에서는 실행 중인 쪽이 정해진 지점에서 스스로 실행을 넘깁니다. 코루틴은 일시 중단 지점에서 상태를 저장하고 반환하는 것으로 실행을 넘기므로 비용이 작습니다. 대신 일시 중단 지점이 없는 긴 계산을 하면 그동안 같은 스레드의 다른 코루틴은 실행되지 못합니다.

</def>
<def title="Q) 코루틴 안에서 Thread.sleep 을 쓰면 어떻게 되나요?">

`Thread.sleep`은 코루틴이 아니라 스레드를 멈추므로, 그 스레드에서 실행될 다른 코루틴도 함께 기다립니다. `runBlocking` 안에서 두 코루틴이 각각 `Thread.sleep(500)`을 하면 둘이 차례로 실행되어 약 1초가 걸립니다. `delay(500)`이었다면 둘 다 약 500ms에 끝납니다.

블로킹 함수를 피할 수 없다면 `Dispatchers.IO`처럼 블로킹을 감안해 스레드를 넉넉히 둔 디스패처에서 실행해야 합니다.

</def>
<def title="Q) 스택리스 코루틴과 스택풀 코루틴은 무엇이 다른가요?">

스택리스 코루틴은 코루틴마다 전용 호출 스택을 두지 않습니다. 코틀린은 `suspend` 함수마다 상태 객체를 만들어 일시 중단 지점을 넘는 지역 변수만 저장하고, 상태 객체들이 서로를 가리키는 `Continuation` 사슬로 돌아갈 곳을 기억합니다. 그래서 `suspend` 함수 안에서만 일시 중단할 수 있습니다.

스택풀 방식은 코루틴마다 전용 스택을 두고 일시 중단할 때 스택을 통째로 보관합니다. 고 언어의 고루틴, JVM의 가상 스레드가 이 방식입니다.

</def>
<def title="Q) 코루틴이 스레드를 대체하나요?">

그렇지 않습니다. 모든 코드는 스레드 위에서 실행되며 코루틴도 예외가 아닙니다. 코루틴은 할 일과 진행 상태를 담은 객체이고, 실제 실행은 디스패처가 고른 스레드가 맡습니다.

코루틴이 하는 일은 기다리는 동안 스레드를 놓아줘서 적은 수의 스레드로 많은 작업을 처리하게 하는 것입니다. 재개될 때는 디스패처에 따라 같은 스레드나 다른 스레드에서 이어 갑니다.

</def>
